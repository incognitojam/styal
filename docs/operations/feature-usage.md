# Feature usage

Monitor [Styal Feature Usage & Browser Health](https://eu.posthog.com/project/120501/dashboard/1026404) in PostHog. It includes adoption, daily rollout coverage, calls by action, outcomes, and successful-call latency by action and server version. Its default date range is 30 days; the date selector applies to every insight.

The dashboard reports adoption as unavailable until it sees an instrumented active cohort. Empty browser charts before the instrumentation ships are expected. Use common metadata filters such as server version or platform; filtering on browser-only properties such as action or outcome removes the active-turn denominator and invalidates adoption.

`feature.used` events use the existing PostHog identity, delivery queue, and telemetry opt-out. The existing browser dashboard filters `feature = browser-tools` and `source = agent`, so adding other feature events does not change its meaning.

Upstream's request counts share the `feature.used` name. They have a dotted `feature` such as `thread.fork`, `editor.open` or `pull_request.action`, an optional `variant` from a contract enum, `surface` when the client reports one, and no `source`, `outcome` or `durationMs`. Filter on `feature` or `source` so the two vocabularies do not mix. Requests the fork already reports are left out of upstream's counts: Device panel opens (`devices`), workflow approvals (`workflow-approvals`), and thread settles and archives (`client.thread.settled`, `client.thread.archived`).

Upstream's `mcp.tool.invoked` records one event per agent MCP tool call with `tool` (the `t3_*` and other tool names), the caller's provider driver, `outcome` with a closed `errorCode`, and `durationMs`; handoff tools such as `delegate_task`, `t3_thread_launch` and `t3_thread_send` add the caller's model, origin and delegation depth, the settings chosen, and each receiving thread's provider, model and modes. `mcp.delegated_task.finished` records each app-owned delegated task's final status, both providers and models, and its runtime. Browser (`preview_*`), device (`device_*`), hardware (`hardware_*`) and `watch_workflow_run`/`unwatch_workflow_run` calls are left out of `mcp.tool.invoked` because they report `feature.used` above.

Additional measured operations are:

- `integration-settings`, `source = user`: `change_requested` records an explicit request to change `browser_access`, `device_support`, `device_access`, `device_idle_shutdown`, or `device_sharing`, with `settingScope = environment | project`. This measures UI requests, not successful writes. Reports require client vocabulary version 14 and contain no setting values, environment or project identifiers, names, or addresses.

- `pull-request-deployments`, `source = user`: `open_environment`, `open_logs`, and `show_all` record explicit deployment panel actions with `outcome = success | failure`. Link success means the browser accepted the handoff, not that the destination loaded. Display, polling, rerenders and Show less do not emit events. Reports require client vocabulary version 2 and go to the PR's environment without names, URLs, repositories, PR numbers or commit hashes.

- `pull-request-bypass-merge`, `source = user`, `action = merge`: pressing **Bypass rules and merge** on web or desktop, with `outcome = success | failure`. It requires client vocabulary version 12. Mobile bypass merges are not reported. Repositories and pull request numbers are never reported.
- `incoming-share-thread`, `source = user`, `action = added`: choosing an existing thread for content shared to the mobile app from another app, with `outcome = success | failure`. Success means the content reached the thread's draft, not that it was sent. Shares started as new threads are not reported. It requires client vocabulary version 16. Threads, projects and shared content are never reported.
- `devices`, `source = user`: Device panel open, close, shutdown and device actions from a client that reports its surface. Requests forwarded from another environment and older clients without a surface remain unattributed instead of being counted again as manual use.
- `devices`, `source = agent`: public list, open, close and screenshot tools, including failed selection and unavailable hosts. Agent-device CLI interactions are not measured. Exclude discovery (`list`) and cleanup (`close`/`shutdown`) when reporting successful adoption; use `open`, `snapshot` and deliberate device actions. Failure reasons are bounded categories, never error messages; `in_use` marks an agent open refused because another thread is using the device, so count it as contention rather than an operation failure. With `deviceUsageVersion = 2`, `timeout` separates boots that ran out of time, killed helper commands and device environments that stopped answering from `operation_failed` and `unavailable`.
- `simulator-memory`, `source = system`, `action = prepare`: each iOS simulator start through styal that finds the simulator stopped and unclaimed, reported by the environment that owns the simulator, including starts requested by another environment. `memoryMode` is the saved preference and `durationMs` covers memory preparation only. `memoryResult` is `applied` (SimSlim set the mode), `unchanged` (Standard on a host without the helper, or another tool started the simulator during setup), or a fallback that started the simulator normally: `fallback_runtime` (iOS older than 18.5), `fallback_host` (not an Apple Silicon Mac), `fallback_helper` (the helper could not be installed), `fallback_check` (Standard could not check the helper). Failures use the device failure reasons and fail the open. Opens of running or held simulators and the fallback for an older device environment are not reported. Filter `simulatorMemoryUsageVersion = 1`.
- `hardware`, `source = agent`: `list`, `acquire`, `call` and `release` tools; `call` adds `hardwareTier` (`read`, `operate`, `approve`). Proxied script calls are not measured. Failure reasons are bounded: `in_use` (another thread holds the device), `declined` and `approval_timeout` (the user's answer), `refused` (no lease, paused, or access off), `device_unreachable`, `invalid_request`, `unavailable`. Count `in_use`, `declined` and `refused` as contention or user choice, not breakage.
- `hardware`, `source = user`: `revoke`, `pause`, `resume`, `keep`, `accept_definition` and `set_credential` from a client that reports its surface.
- `project-file-approvals`, `source = user`: `review`, `approve` and `revoke` of a `styal.json` action that runs on worktree creation or settle, from a client that reports its surface. Failure reasons are bounded: `not_found` (the project or action is gone, usually a stale review), `invalid_request` (the action runs on no trigger), `refused` (no settings access). Count `not_found` as a stale view, not breakage.
- `workflow-approvals`, `source = user`, `action = approve`: pressing **Approve workflows to run** in the pull request panel, from a client that reports its surface. It counts approvals on fork pull requests and on pull requests whose head a workflow's `GITHUB_TOKEN` pushed; styal surfaced only the fork case before. Repositories, pull request numbers and workflow names are never reported.
- `web-build-update-notice`, `source = user`, `action = refresh_requested`: explicit web refresh clicks. Matching `feature.exposed` events with `source = system`, `action = notice_shown` count visible notices separately; they are not usage. Notice exposure is counted once per build per loaded page through one supported paired environment, after that server accepts the report; skipped or failed attempts allow a later sighting to retry. If a blocked reload leaves the page open, another refresh attempt is allowed after two seconds. A refresh request does not establish that the new bundle loaded.
- `desktop-update-notice`, `source = user`, `action = release_notes_opened`: **Release notes** clicks on the notice the desktop app shows after starting on a newer version. Matching `feature.exposed` events with `source = system`, `action = notice_shown` count notices shown, at most once per version per window load, through the primary environment once it supports client vocabulary version 5; only desktop surfaces are recorded. Versions are not reported beyond the existing `clientAppVersion` attribution. A first run, a downgrade, and a lower-version channel switch show no notice.
- `combined-update-confirmation`: web and desktop sidebar update confirmations emit `feature.exposed`, `source = system`, `action = shown` once after inspection requires confirmation, and `feature.used`, `source = user`, `action = confirmed | cancelled` for the first explicit decision. Cancel and Escape count as cancellation; programmatic closes and unmounts do not. Loading inspections, automatic updates when all work can continue, rerenders and repeated clicks do not add events. Reports require client vocabulary version 15 and use one supported paired environment, preferring the primary and keeping the decision on the exposure's environment. Delivery is best effort and never delays updating. Confirmation measures intent, not installation success. Machine, provider and thread names, update versions and dialog content are never reported.
- `diff-file-review-order`, `source = user`: `relevance_selected` and `alphabetical_selected` record explicit changes to the local sort preference from the Changes view or pull request Code tab on web and desktop, and from the review sheet or pull request file menus on mobile (`view = changes | pull_request`); `surface` separates them. They do not count readers who keep the default or establish whole-feature adoption; alphabetical selections can indicate rejection of the default.
- `mentioned-time-chips`, `source = user`, `action = details_opened`: opening a time explanation by hover or focus, at most once per mounted chip. Reopening the same chip does not add an event; remounting it can. This bounds repeated-hover traffic while delivery is backed off. Incidental hover is possible, and missing interactions do not mean the chips were unseen or unhelpful. Written times, timezones, and message content are never reported.
- `next-unread-thread`, `source = user`: `opened` when **Go to next unread thread** opens a thread, with `attention` naming what that thread was waiting for (`approval`, `input`, `limited`, `failed`, `woke` or `done`), and `nothing_waiting` when no thread needs the user, both with `entryPoint` (`shortcut`, `command_palette`, or `chip` for the button above the composer). Reports go through one supported primary environment and require client vocabulary version 9; `chip` requires version 10. Thread names and keys are never reported.
- `project-actions`, `source = user`, `action = run`: running a project action from the web or desktop actions menu or its shortcut, once the terminal accepts the command, carrying `actionSource` (`local` for an action saved in styal, `file` for one read from the project's `styal.json`, `override` for a saved edit of a `styal.json` action) and `projectFile` (`styal.json`, `t3.json` or `none`: the project file in effect at the project root, so adoption of each file and of actions kept only in styal shows). It requires client vocabulary version 4. Setup and settle runs and mobile runs are not reported. Action names, ids and commands are never reported.
- `setup-thread-settlement`, `source = user`, `action = continued`: leaving the welcome wizard's Workflow step with **Finish**, carrying the chosen `settleOnMerge` and `settleWhenInactive`. It is reported once through the first selected computer that supports automatic settlement, and requires client vocabulary version 3. Setup that skips the step, such as hosted setup for computers that already have work, does not report; compare `false` choices with the total to see how many users turn a rule off.
- `sidebar-project-filter`, `source = user`: `filter_set` and `filter_cleared` record explicit changes to the sidebar's project filter, with `entryPoint` naming where the change was made (`filter_menu` for the menu beside the sidebar search, `project_menu` for a project's context menu, `thread_menu` for a thread's context menu). Clearing a filter whose project disappeared is not counted. `thread_started` records the new-thread actions that resolve their project from context (sidebar New, `chat.newLocal`, the palette's New thread item, a project's New thread menu item, and `chat.new` where it does not open a project list) taken while a filter is applied. Choosing a project from the palette's New thread in… list is not counted. The filter is a device preference, so both use one supported primary environment. Project names and keys are never reported, and both require client vocabulary version 4. A filter that stays applied for days produces no change events, so use `thread_started` for ongoing use.
- `sidebar-project-groups`, `source = user`: with threads grouped by project, `reordered` (an unpinned project's header dragged to a new place), `pinned`, `unpinned`, `pins_reordered` and `archived`, with `entryPoint` (`header_drag` or `header_menu`). Pin and archive changes are counted after their write succeeds. Reports go through one supported primary environment and require client vocabulary version 8. Pins and archives made in Settings, the sidebar project filter or the command palette are upstream entry points and are not counted. Project names and keys are never reported.
- `workflow-run-watch`, `source = agent`: `watch` and `unwatch` record each `watch_workflow_run` and `unwatch_workflow_run` call with `watchResult` (`started`, `already_watching`, `already_completed`, `stopped`, `not_watching`). Failures carry `failureReason` (`read_failed`, `invalid_target`, `refused`, `unavailable`, `operation_failed`). `already_completed` is a call that needed no watch, not adoption.
- `workflow-run-watch`, `source = system`, `action = end`: the server records how each watch it saw ended: `endReason = completed` with `conclusion` (`success`, `failure`, `cancelled`, `timed_out`, `skipped`, `other`), `unreadable` after eight failed reads, or `stopped` for unwatch, settle, archive and Stop, plus `watchedMinutes`. A watch that starts and ends between two passes, or ends while the server is down, has no end event. Use `completed` ends to see whether watches deliver a wake; `stopped` includes agent unwatches already counted above. Run IDs, repositories, URLs and workflow or job names are never reported.
- `workflow-run-watch`, `source = user`, `action = review`: approving or rejecting a watched run's deployments from the thread, with `reviewState` (`approved`, `rejected`), from a client that reports its surface. Recorded from `workflowRunWatchUsageVersion = 2`. Environments, comments and run data are never reported.
- `delegated-wake`, `source = agent`, `action = delegate`: each `delegate_task` call with the wake it chose, `wake = each` (including calls that omit it) or `wake = all`, and for `all`, `wakeAfter` (whether `wakeAfterMs` was set), plus the call's `outcome`. The share of `all` calls is adoption; wakes themselves are not counted. Filter `delegatedWakeUsageVersion = 1`. Prompts, task IDs and timeout values are never reported.
- `desktop-update-idle-restart`, `source = system`, `action = would_restart`: macOS desktop apps measure when an idle restart could install a background-staged update, without installing it. Each staged version reports once: `delayBucket` (`<1h`, `1-8h`, `8-24h`, `>24h`) is the time from staging to the first moment the system was idle for five minutes or locked while no host had a waiting approval or question, a running turn that thread continuation will not resume, a provider install, devices used by another environment, or a failed activity check; `installed_first` means the update installed through a quit or the restart button before any idle moment, and `never` means a channel change discarded it first, or the app quit without installing it; both are reported on the next launch or at the discard, best effort. `updateVersion` is the staged version. The desktop app sends the observation through its backend's telemetry pipe, so it carries that server's identity and opt-out; filter `desktopUpdateIdleRestartUsageVersion = 1`.

## Desktop launch timing

Desktop apps send one `desktop.launched` event per launch, once the main window first shows, through the bundled backend's telemetry pipe, so it carries that server's identity and opt-out. It is not a `feature.used` event. `desktopPlatform` is the desktop app's own platform, which differs from `platform` when the primary backend runs in WSL. `backendReadyMs` and `windowShownMs` count from the process start; `backendReadyMs` is null when the local environment is off. `launchKind = update` marks the launch of the version an in-app update restart installed and adds `updateStopMs` (the restart's acceptance until the installer handoff, mostly stopping backends), `updateRelaunchMs` (the handoff until the new process started, including staging at the restart, installation and relaunch), `updateTotalMs` (the sum of both plus `windowShownMs`) and `stagedInBackground` (macOS: staged when it downloaded). A launch back on the old version and an install on quit are `normal`. A window that never shows sends nothing. Compare `updateTotalMs` by `desktopPlatform` and `stagedInBackground` to judge whether update restarts go unnoticed, and `windowShownMs` of `normal` launches for cold starts; events arrive only from builds with this instrumentation, so no version property is needed.

## Thread settle reasons

Servers with `threadSettleReasonUsageVersion = 1` record each automatic settlement as `server.thread.settled` with `reason = merged | closed | inactivity`; inactivity adds `afterDays`, the threshold that applied. A merged or closed reason is the one pull request that decided the settle: any open linked pull request blocks automatic settlement, and otherwise the most recently merged or closed one counts. The existing `client.thread.unsettled` event adds `previousSettleReason` (`user`, `merged`, `closed`, `inactivity`, or `unknown` for a thread that was not settled or settled before reasons were recorded). To measure how often each automatic rule is undone, divide `client.thread.unsettled` by `server.thread.settled` per reason, restricted to servers with the version property. Threads, projects, titles and pull request numbers or links are never sent.

## Auto mode health

`provider.turn.completed` carries `runtimeMode` and, from servers that count them, `approvalRequests`: the command, file and permission approvals the turn raised (questions are not counted). Auto is opt-in, so these turns come from users who chose it. Watch the share of `runtimeMode = auto` turns with `approvalRequests > 0`, broken down by `provider` and provider version. A jump after a provider release means its reviewer is asking about routine work. Filter on `approvalRequests` being set, since older servers do not send it. The provider canary's `auto` scenario checks the same thing before managed updates install a release.

Codex Auto turns also carry the reviewer's own verdicts: `autoReviewsApproved`, `autoReviewsDenied`, `autoReviewsTimedOut` and `autoReviewsAborted`. Denials are actions the reviewer stopped without asking anyone; denials divided by all verdicts is its block rate. Other providers and modes leave these fields out.

## Provider inventory and updates

Servers with `providerAnalyticsUsageVersion = 1` send two provider events. They are not `feature.used` events and are not on the feature dashboard.

- `provider.inventory`: one event per configured provider instance, two minutes after startup and then every 24 hours while the server runs. Properties: `driver`, `instance` (`default` or `custom`; custom instance names are never sent), `installed`, `enabled`, `status` (`ready`, `warning`, `error`, `disabled`), `version` (plain `x.y.z` or null), `installerKind` (`npm`, `bun`, `pnpm`, `yarn`, `volta`, `vite-plus`, `homebrew`, `native` for the provider's own updater, `unknown` when styal cannot update it), `canAutoUpdate` (the installer can pin the verified version), `autoUpdatesEnabled` (update checks and automatic updates both on), `testedVersion` (the newest version the provider canary verified for this install, whenever one is known, else null), `autoUpdateTargetVersion` (the verified version when it is newer than the installed one, else null), `autoUpdateBusySkips` (background updates of this instance skipped since the previous report because a thread using its CLI was active or waiting; skips because another server held the install lock are not counted) and `selfUpdaterActive` (true while the provider's own scheduled updater still owns the install, false once it is off, null when styal cannot tell or cannot detect it for this installer; only native Claude Code installs on macOS, Linux, and Windows, and standalone Codex installs on macOS and Linux, report true or false). Instances whose driver this build does not have are left out.
- `provider.update.finished`: one event per manual or background update that started, plus manual updates refused because another install held the lock. A background update dropped before it starts, including one dropped because the lock was held, is not counted. Properties: `source` (`manual` or `background`), `takeover` (true for a background reinstall of the version already installed, which turns off the provider's own updater; a takeover succeeds only when that updater is off afterwards, else it is `unchanged` with `unchanged_after_install`), `driver`, `installerKind`, `fromVersion`, `targetVersion` (null for an unpinned update), `resultVersion`, `outcome` (`success`, `failed`, `unchanged`), `failureReason` and `durationMs`. `failureReason` is null on success and otherwise one of `install_in_progress` (manual update refused by the install lock), `installation_changed`, `version_rejected` (refused before running), `timeout`, `permission_denied`, `command_failed`, `spawn_failed` (the installer ran and failed or could not start), `not_installed_after_install`, `unchanged_after_install`, `provider_error_after_install` (the installer exited 0 but the result did not verify), `interrupted` or `internal_error`. Installer output, commands, paths and error messages are never sent.

Installations by installed provider: count distinct identities of `provider.inventory` events with `installed = true` and `buildKind = release`, broken down by `driver`, over a window of at least one day. An identity can report several instances of one driver. Providers that are behind and not updating are inventory events where `autoUpdateTargetVersion` is set; break them down by `autoUpdatesEnabled`, `canAutoUpdate` and `autoUpdateBusySkips > 0` to separate disabled updates, unpinnable installers and busy hosts. Providers ahead of the tested version, usually moved there by their own built-in updater, are inventory events whose `version` is newer than `testedVersion`. Takeover coverage is the share of inventory events with `selfUpdaterActive` set that report false; events on the tested version with `selfUpdaterActive = true` are installs a takeover is still pending for. For update reliability, break `provider.update.finished` down by `source`, `installerKind` and `failureReason`.

## Settings snapshot

Servers with `simulatorMemoryUsageVersion = 1` also report `simulatorMemoryMode` (`standard` or `low-memory`) and `projectsWithLowMemoryMode` in `settings.snapshot`. These measure the saved startup preference, not applied profiles or memory savings. Project identifiers and capability lists are not reported.

Servers with `settingsSnapshotUsageVersion = 1` send one `settings.snapshot` event two minutes after startup and then every 24 hours while the server runs. It is not a `feature.used` event. Every property below is sent on every report, whether or not it is at its default, so a missing property means an older server rather than an unchanged setting.

- New threads: `defaultRuntimeMode`, `defaultThreadEnvMode` (`local`, `worktree`, or null to inherit the repository's styal.json or legacy t3.json), `defaultModelSelectionSet`, `responseStreamingMode`, `continueThreadsAfterServerUpdate`.
- Worktrees and projects: `newWorktreesStartFromOrigin`, `worktreeSubmodules` (null to inherit), `worktreesDirectoryCustomized`, `defaultAutoPull`, `defaultProjectScriptCount`, `projectsWithOverrides` (projects with at least one project-level setting), `repositoriesWithApprovedFileActions` (repositories with at least one approved styal.json action).
- Thread settlement: `sidebarAutoSettleOnMerge`, `sidebarAutoSettleAfterDays` (null when off), `sidebarAutoSettleKeepPullRequests`, `snoozeLimitedThreads`, `autoResumeLimitedThreads`, `compactIdleThreads`.
- Source control writing: `branchNamingMode`, `branchNamePrefixCustomized`, `textGenerationModelCustomized`, `sourceControlWriterModelSet`, `sourceControlWritingStyleMode`, `followChangeRequestTemplates`, `removeAgentCreditsOnMerge`, `pullRequestMergeMethod` (null reuses the device's last choice), `reviewGuidesEnabled`, `reviewGuideModelSet`, `reviewGuideInstructionsCustomized`.
- Storage cleanup, environment-wide: `worktreeCleanupKeepWhen`, `worktreeCleanupAfterDays`, `worktreeCleanupOnMerge`, `worktreeCleanupOnDelete`, `worktreeCleanupUnchanged`, `browserArtifactsCleanupAfterDays`, `logsCleanupAfterDays` (day counts are null when off).
- Agent access and devices: `enableAgentBrowserAccess`, `enableAgentDeviceAccess`, `enableAgentHardwareAccess`, `enableDeviceSupport`, `deviceIdleShutdownMinutes` (null keeps devices running), `keepPhysicalAndroidScreensOff`.
- Usage: `cursorKeychainUsageEnabled`.
- `backgroundActivityProfile` (`balanced`, `performance`, `battery-saver`, `custom`).

Values are booleans, enum literals and small integers. Paths, branch prefixes, instructions, model and instance IDs, and the contents of per-project settings are never sent; they appear only as `...Customized`, `...Set` or a count. Provider update settings are covered by `provider.inventory`. Client preferences such as the send shortcut, follow-up behavior and sidebar sorting are stored on each device; `client.settings.snapshot` below reports them.

To judge a default, filter `buildKind = release`, take each identity's latest snapshot in a window of at least a day, and compute the share of identities whose value differs from the default, per property. A high share for one value suggests a different default or a setup step; a low share means the default holds. Events carry no server ID, so when one identity runs several servers, such as a laptop and a desktop signed in to the same provider account, its latest snapshot comes from whichever server reported last. Project-level overrides are not broken down by key.

[Styal Settings Defaults](https://eu.posthog.com/project/120501/dashboard/1043695) in PostHog runs this query over the last 7 days and charts how many release identities report each day. Its table lists each setting's shipped default; update that list when a default changes, or the `is_default` column will mark the wrong value.

When adding a server setting, either report it here or list it with a reason in `NOT_REPORTED` in `SettingsSnapshot.test.ts`; that test fails until you choose.

`browserToolsUsageVersion`, `deviceUsageVersion`, `workflowRunWatchUsageVersion` and `settingsSnapshotUsageVersion` identify server instrumentation separately. They indicate collection support, not feature availability or compatible client coverage. Keep the legacy `featureUsageVersion = 1` filter only for the existing agent-browser cohort. Do not interpret a missing event from an older client or an unavailable device host as non-use.

`forkClientUsageVersion` marks only these client observations, not all clients connected to a reporting server. Compare refresh requests with exposed identities; it cannot define a denominator of all active instrumented clients. Unpaired clients and servers without a compatible reporting vocabulary are outside coverage. The server advertises its vocabulary in `capabilities.forkClientUsageVersion`; clients skip reporting if that version is below `FORK_CLIENT_USAGE_VERSION`. Diff and time interactions use the owning environment; the page-level update notice uses one supported primary environment. Build IDs stay client-local for deduplication, and telemetry failures can lose observations. The existing agent-browser dashboard does not include these events; filter by the feature, event and action above to inspect them.

`buildKind` distinguishes release, development and test processes. Release workflows stamp the bundle explicitly; a local build is development even when its package version resembles a release. `releaseChannel` is stable, nightly, preview or unknown. Upstream's `telemetryChannel` property is `dev` on every styal build, because only T3 Code's own release workflows stamp it; use `buildKind` and `releaseChannel` instead. Test and CI processes default to telemetry disabled; opt-in verification must point at a local collector or a separate analytics project, not the production project.

For the existing agent-browser adoption chart, count distinct reporting identities that successfully perform an action, excluding `status` probes. Compare them with distinct identities with `provider.turn.completed` in the same period. Restrict both cohorts to `featureUsageVersion = 1`, and intersect the feature cohort with the active cohort. For features with server instrumentation versions, use the corresponding version on both cohorts and filter `buildKind = release`. These server version properties are attached to every analytics event, so earlier installations cannot silently enter the denominator. Keep the release/version breakdown and compatible-client limitations when comparing periods across rollout.

This estimates adoption among active reporting identities, not every user. Telemetry opt-outs are absent, the identity may represent an account or an installation, and some active environments have no compatible desktop browser host. A low rate is evidence to investigate availability and discoverability before removing a feature. Track failed attempts separately from successful adoption; an unavailable feature can have demand without successful uses.

For reliability, include every action and outcome, then break down failures and p50/p95 `durationMs` by action and server version. Browser snapshot outcomes include saving a requested screenshot, and recording-stop outcomes include transferring its artifact. Internal status requests for tool icons do not emit additional usage events.

## Client settings snapshot

Web and desktop clients with `forkClientUsageVersion >= 8` send one `client.settings.snapshot` event per device per day. It is not a `feature.used` event. The client reports through its primary environment, or on hosted web through the first paired environment that accepts the vocabulary, and starts the next day only after that server accepts the report. Windows on one device share the day through local storage; a report that fails, for example before the socket reconnects, is retried a minute later, with the wait doubling after each further failure up to an hour. The pending retry is stored with the day, so a reload or reconnect does not retry early. A client older than the server leaves out settings added after its version; those properties are absent rather than set to a default, so count them as unknown, not as a choice. Events carry the reporting server's identity plus `surface`, `clientOs` and `clientAppVersion`. Mobile reports its own settings under the same event; see [Mobile settings](#mobile-settings).

## Device stream quality

Web, desktop and mobile viewers with `forkClientUsageVersion >= 18` send one `device.stream.summary` event when a device stream that showed video for at least five seconds closes or restarts, through the device's environment. It is not a `feature.used` event; Device panel opens are already counted under `devices`. Properties: `platform`, `transport` (`h264` for Android, `avcc` or `mjpeg` for iOS), `connection` (`loopback` when the viewer reached the server on the same machine, otherwise `network`), `durationSeconds`, `averageFps`, `decoderResets`, `reconnects`, and for Android `stalls` (gaps of at least two seconds without video; Android keeps sending frames on a still screen) and `longestGapMs`. `maxAddedDelayMs` is the largest growth in delay behind the device's capture timestamps during the stream, taking the least-delayed frame in each second in which at least five frames arrived, so an encoder holding back sparse frames on a still screen does not count; a rising value means video queued between the device and the viewer. It is null for iOS and for streams whose screen never moved. Mobile reports the latest summary the viewer sent, which can miss up to ten seconds at the end of a stream. Device names, identifiers and addresses are never reported.

- Composer and conversation: `sendShortcut`, `followUpBehavior`, `composerRichTextEnabled`, `composerCollapseOnScroll`, `persistComposerContextStrip`, `proactivePanelsEnabled`, `showSkillsInSlashMenu`, `planModeEnabled`, `contextWindowMeterEnabled`, `turnUsageEnabled`, `turnUsageFigure`, `chatWidth`, `wordWrap`, `mathRenderingEnabled`, `timestampFormat`, `loadBalancingEnabled`.
- Sidebar: `legacySidebarEnabled`, `sidebarWorkingShelfEnabled`, `sidebarThreadGrouping`, `sidebarProjectGroupingMode`, `sidebarProjectGroupingOverrideCount`, `sidebarProjectSortOrder`, `sidebarManualProjectOrderSaved` (the device has dragged projects into an order; the order is kept even while another sort is selected), `sidebarThreadSortOrder`, `sidebarThreadTimestampMode`, `sidebarThreadPreviewCount`, `confirmThreadArchive`, `confirmThreadDelete`, `confirmThreadUnpin`.
- Notifications: `notificationMode`, `inAppNotificationsEnabled`, `completionSound`, `inputSound`, `approvalSound`, `claudeStatusAlertsEnabled`, `openaiStatusAlertsEnabled`, `githubStatusAlertsEnabled`.

### Mobile settings

The mobile app sends `client.settings.snapshot` with `surface = mobile` once a day per phone, through the first connected environment with `forkClientUsageVersion >= 17`, on the same schedule as web. Every property is sent on every report; a preference the user never touched is sent as the default the app applies. Filter `surface = mobile` before taking the latest report per identity, because the same server identity also receives web and desktop reports.

## Provider stall detection

Provider stall detection emits `provider.turn.stall` with `outcome = detected | activity | waiting |
run_ended`, `phase = startup | provider_silent`, provider type, `quietDurationMs`, and
`incidentDurationMs`. Each episode emits once when detected and once when cleared; repeated
sweeps and reconnects do not emit again. Filter on `providerStallUsageVersion = 1` for rollout
coverage. These are suspected stalls, not confirmed provider failures: quiet reasoning can
resume normally. Compare detection counts and clearance outcomes by phase and server version;
completion-only cohorts omit turns that never finish. Telemetry is best effort and follows the
existing opt-out. Durable thread notices provide local evidence independently of telemetry.

## Measure a fork feature

Measure use of a new or materially changed fork feature in the PR that ships it. Measure fork-maintained behavior only: usage of an upstream feature does not inform whether to keep a fork difference.

- **Server-observable operations:** extend the fixed vocabulary in `apps/server/src/telemetry/FeatureUsage.ts` and observe each public operation once at the owning entry point. Agent tools record `source = agent`. Client RPCs record `source = user` through `apps/server/src/telemetry/ClientFeatureUsage.ts`, which skips requests without a client surface so a request relayed from another environment is not counted twice. Add a `<feature>UsageVersion` property in `AnalyticsService.ts` so adoption can be restricted to servers that report the feature.
- **Client-only interactions:** extend the allowlisted `ForkClientUsageInput` contract and increment `FORK_CLIENT_USAGE_VERSION` instead of adding a protocol method per feature; reports go through `server.reportForkClientUsage`. New vocabulary versions retain previous inputs for older clients. A newer client requires its complete vocabulary, so it also skips otherwise compatible observations against an older reporting server.
- **Upstream conflicts:** prefer observing an existing operation over adding protocol, contract or authorization changes, and keep event definitions and reporting code in fork-owned files.
- **Coverage:** include each applicable manual and agent entry point before interpreting the count as whole-feature adoption.
- **Failures:** map expected refusals to their own bounded `failureReason`, so they are not counted as broken operations.
- **Content:** send structural metadata only; never pass operation arguments, results, names, URLs, paths, selectors, page content, or screenshots.
- **Records:** list the feature's events above, describe what is collected in [Product usage data](../user/telemetry.md), and test that each operation records one event with its outcome and no operation data.
