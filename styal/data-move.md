# Moving today's styal data to the restart

Use the restart checkout and its dependencies. These commands run from `apps/server` on an **offline file supplied as a snapshot**. Never give them the live database or a file below `~/.styal`. Do not copy settings, credentials, relay configuration or updater state into a rehearsal. Keep the original snapshot; every failed step means discarding the working copy and starting again from a fresh snapshot, including failures partway through migration. The archive retains original bytes and credentials: this is not a support export.

## Rehearsal

1. Put the supplied snapshot in a private directory outside `~/.styal`, with enough space for an additional database and a staged runtime (several GB). Set `HOME` to a new synthetic directory, unset `T3CODE_PORT`, and set `T3CODE_DEV_SEED=0`, `T3CODE_TELEMETRY_ENABLED=false`, `DO_NOT_TRACK=1`, `T3CODE_ERROR_REPORTING_ENABLED=false`. Use a direct Node runtime if changing HOME confuses a version-manager shim.
2. Run `vp run data-move:preflight <copy>`, then `vp run data-move:archive <copy>`, `vp run data-move:neutralise <copy> rehearsal`, and `vp run data-move:migrate <copy>`. Review each report before continuing.
3. Build the restart server and client (`vp run --filter t3 build` from the repository root). Set `STYAL_REHEARSAL_CHROMIUM` to an installed Chromium executable (its containing runtime directory is copied). Run `vp run data-move:rehearse <copy>` from `apps/server`. Linux and working bubblewrap user/mount/network namespaces are required; failure refuses startup, with no fallback.
4. Open the printed **loopback bridge URL** in a browser on this machine. Check projects, thread lists, archived/forked threads and message history. Check startup's resolved base directory is `/rehearsal/base` (the database is under `userdata`) inside the printed rehearsal directory. Repository paths are deliberately invisible; file, git, terminal and provider actions can fail. The browser runs inside the isolation; the host page is a fixed image viewer with click, keyboard, scroll, Back and Refresh view controls. It cannot open copied links or resources on the host. Use Refresh view after asynchronous changes. Settings are fresh safe defaults, not a copy of the live settings. Do not send messages in copied threads.
5. Stop with Ctrl-C. Discard the printed `styal-rehearsal-*` directory and working database when finished. The supplied snapshot was never started or rewritten by the launcher.

The [launcher](../apps/server/src/persistence/dataMove/rehearse.ts) stages its runtime and a second database copy in a fresh sibling directory. Bubblewrap exposes only that directory, read-only system runtime files and isolated `/proc` and `/dev`. Its network namespace has loopback only; the server and Chromium share it. A seccomp filter restricts sockets to Unix/IPv4/IPv6 and namespace-local route netlink, and blocks io_uring and compat syscall ABIs, preventing non-namespaced socket families such as VSOCK from bypassing that boundary. A reverse Unix-socket bridge in a read-only control directory exposes only the image viewer through an ephemeral host-loopback listener; it offers no general network proxy or host-side app rendering. All descendants inherit the isolation, including commands started by clicking in the UI. Do not bypass the launcher to inspect a rehearsal copy.

## Cutover

1. Stop today's server and keep today's build and database intact. Obtain the final offline snapshot, including whatever WAL handling the snapshot method requires. Put a working copy outside `~/.styal`; run preflight → archive → neutralise **cutover** → migrate as above. Do not reuse the rehearsal copy.
2. With both servers stopped, place the successfully moved file at `<restart-base>/userdata/statev2.sqlite` in a separately provisioned restart base directory. Do not overwrite today's database. Provision any required attachments and explicitly reviewed settings separately; this procedure moves the database only.
3. Start the restart build explicitly with `--base-dir <restart-base>`. Check the resolved data directory, startup errors, projects, thread/fork history and attachments, held queues, schedules, provider configuration and remote access before accepting new work. Do not automatically release old queued messages.
4. To go back, stop the restart build and start today's build against today's untouched base directory. Work created after cutover is not copied back by this procedure.

[Neutralisation](../apps/server/src/persistence/dataMove/neutralise.ts) cancels in-flight work, expires pending requests and ends PR watches. Ordinary queued user messages remain held for explicit resumption. A remote delegated child can still be running elsewhere: the report counts children without confirmed stop, and local cancellation does not stop them. Accepted webhook work is failed, checkpoint captures and attachment cleanups are cancelled (a cut-off turn can lose its checkpoint/diff; orphan attachments can remain), and cancelled title work can leave placeholder titles. Schedules remain configured for cutover; rehearsal additionally disables them and removes authentication, pairing, peer and provider-resume authority and expires shares. Review the neutralisation impact report before cutover.

Open points before using real data: the snapshot/export method, avoiding stalls while obtaining any rehearsal snapshot, WAL/checkpoint consistency, placement of attachments and reviewed settings, and the operational restart base/service configuration. These are not settled by this launcher or by synthetic proofs.

## If main gains a migration before cutover

Stop cutover. First search the old source pin with `rg 68e0ea592ac9a2262d04f2457d83e3f21d73ac73 apps/server/src/persistence/dataMove` and update generator guards, witness revision tags and test fixture schemas together. Update the explicit source revision in `generateSource.ts`; use an offline checkout at that pin with its own dependencies. Run `vp run data-move:fixtures <offline-source-checkout> <synthetic-output-dir>` then `vp run data-move:preflight-fixtures <offline-source-checkout> <synthetic-output-dir>` and `vp run data-move:compatibility-fixtures <offline-source-checkout> <synthetic-output-dir>`. Review every ledger, schema, field and codec difference before replacing source fixtures/inventory. Audit the new migration and source readers/writers against preflight codecs, archive selection/exceptions, neutralisation/recovery and credential handling. Update the explicit leftover allowlist and regenerate `bridgeSchema.json` through the real target migrations on the new synthetic source; re-audit upstream 87–117 and fork 17 for collisions. Repeat both-mode chain, real-service/replay, refusal, failure and scale proofs, independent review, dependency-only and pinned-main stack trials, then `check:changed`. Keep corrections in their owning feature commits. Never just bump ledger constants or accept extra schema objects. Generate a new archive from a fresh source copy.
